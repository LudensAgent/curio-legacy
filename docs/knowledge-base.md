# Java 1.20.1 知识库

`knowledge/minecraft-java-1.20.1/` 是随仓库维护的游戏资料，当前覆盖目标是支撑生存准备、进入下界、获取末影之眼、寻找要塞、进入末地、击败末影龙并返回。它提供可以主动搜索、逐章阅读和继续追问的参考，让 Agent 了解世界规则、条件、例外与可能做法。资料可以涉及当前尚无专用技能的机制；这仍是精选资料，不代表 Minecraft Wiki 全站或全部玩法。

运行时只读本地文档：查询本身不访问网络、不执行游戏动作、不生成行动队列、不登记行为、不把文献写成个人经历或已学技能。维护者在更新资料时核对外部来源，与游戏运行中的查询是两个过程。文献不能证明当前世界存在某个资源、某个物品已经取得或某种方法已经成功。

依赖关系不等于强制科技树：钻石镐与浇筑门、不同珍珠来源、远近程或爆炸战术都保留条件与代价，药水和整套钻石装备不作为通关硬门槛。“进入末地”“击败龙”“存活返回”分别确认；龙蛋、鞘翅、末地城与全进度不是此目标的必需项。

维护时检查依赖是否闭合，例如之眼需要珍珠和烈焰粉，药水还涉及基底、燃料与材料来源。新增资料继续遵守下面的候选数、分页与字节限制，不能随库容量增长而自动扩大注入量。本地测试检查代表问题能否查到资料、链接和来源是否保留；实际自主完成游戏仍需另行运行 Agent 验证，不能用检索测试替代。

## 查询接口

沿用心智的只读查询协议，由模型直接输出一个查询对象：

```json
{"kind":"knowledge","query":"剪过毛的羊怎样重新长毛"}
```

搜索默认只查 Wiki 游戏资料（`mechanic` / `tutorial`），返回精简候选，默认两条、最多三条，同一文档最多一条。每条摘录最多 120 个字符，用于判断相关性；搜索不会自动混入操作手册，也不代表已经阅读了机制的完整条件。可以直接读候选中的章节：

```json
{"kind":"knowledge","id":"animal-husbandry","section":"wool"}
```

还不确定要读哪节时，省略 `section` 只返回轻量章节目录，`document.sections` 为空，`contents` 列出章节 ID 和标题：

```json
{"kind":"knowledge","id":"animal-husbandry"}
```

空查询浏览文档目录；文档目录和章节目录均可按返回的 `nextOffset` 继续传 `offset` 翻页：

```json
{"kind":"knowledge"}
```

```json
{"kind":"knowledge","offset":12}
```

`knowledge` 也可按 `id: "agent-controls"` 显式读取操作手册的章节目录，再指定章节阅读。手册按当前注册接口生成，标记为 `control`，包含接口原有的参数、说明和时限，涵盖基础操作及已有复合动作，不把它们称为 Agent 自学成果。它不进入默认 Wiki 搜索结果。`moves` / `mechanics` 仍可查实际动作接口，`recipes` 查本版本配方和缺口，`recall` 查自己的经历。这些来源的含义保持独立。

搜索结合标题、章节、中文词组、英文名称和别名匹配。搜索和目录的完整 JSON 各不超过 2,400 个 UTF-8 字节；指定章节阅读时，来源、正文和其余返回字段合计不超过 6,000 个 UTF-8 字节。搜索候选省去来源等重复元数据，实际章节阅读才返回正文与来源。所有响应都是完整 JSON，不截断序列化后的对象。

长章节按字符偏移 `cursor` 分页，返回 `nextCursor` 时可以使用它读取下一页；不要从 UTF-8 字节数自行推算字符位置。例如收到 `nextCursor: 900` 后：

```json
{"kind":"knowledge","id":"animal-husbandry","section":"wool","cursor":900}
```

每次思考的所有知识查询返回合计最多 10,000 个 UTF-8 字节，按实际序列化后的 JSON 长度计数，完整响应元数据也在预算内。直接输出查询和把查询误写进行动步骤后由心智代查，共用这项额度；每次新的思考重新计算。后端接收本次剩余额度，必要时缩小当前页，仍返回可解析的完整 JSON；心智预留一条简短耗尽提示，剩余可用额度不足 512 字节时不再读取后端，明确要求根据已读资料决定。知识查询也与其他只读查询共用每次思考最多三次的次数上限，不挤占其他查询的返回字节额度。

查不到意味着本地首批资料没有匹配结果，不代表游戏不存在这种机制；可以换用实体名、物品 ID、中文别名或相邻概念继续查。正文在启动时读取并建立内存索引，更新文件后重启 Agent 生效；没有在线抓取或自动更新，也不需要新依赖或独立数据库。

## 文档格式

每篇一个 UTF-8 Markdown 文件，文件名与稳定的 `id` 一致。开头两行 `---` 之间是受限元数据：每行 `key: JSON值`，**不是 YAML**。字符串、数组和对象均使用合法 JSON，不写 YAML 缩进对象、多行字符串或注释。

```markdown
---
id: "example-mechanic"
title: "示例机制"
kind: "mechanic"
edition: "java"
versions: ["1.20.1"]
aliases: ["中文别名", "item_id", "English name"]
sources: [{"url":"https://minecraft.wiki/w/Example","title":"来源标题"}]
versionNote: "说明已核对的适用范围、排除内容与仍未确认的部分。"
reviewedAt: "2026-10-28"
---

## conditions | 条件与例外

说明机制何时成立、需要什么以及不成立的情形，在相关事实旁标注来源链接。

## effects | 产生什么结果

区分规则预期、实际观测和物资取得。
```

`kind` 使用 `mechanic` 或 `tutorial`。前者说明规则，后者说明一种可选做法与适用条件，不能把攻略写成 Agent 必须遵循的主线。每篇采用少量语义完整的短章节，较长章节通过 `cursor` 继续阅读，正文与来源共同受阅读响应的字节预算约束；`section-id` 使用稳定的小写字母、数字和连字符，标题保留用户可读的中文。相关条目可写成 `[羊毛再生](knowledge:animal-husbandry#wool)`，保持目标文档与章节真实存在。

别名可以包含中文说法、英文名称和游戏 ID，服务于用户实际提问；不要用与正文无关的热词增加匹配。新增章节应独立读得懂，保留前提、例外和必要的版本限制，不依赖把全文同时塞入上下文。

## 来源与版本维护

- 本目录只声明 `edition: "java"`、`versions: ["1.20.1"]`。当前 Wiki 页面往往同时描述最新版、Bedrock 和历史变化；需要核对具体机制在 Java 1.20.1 是否成立，不能给当前网页贴一个版本标签就当作核对完毕。
- 每篇保留来源标题和原始页面 URL，正文使用原创释义并在事实旁链接来源。对教程保留可选性与代价，不大段复制原文；引用图片、转载正文或导入整站资料需要另行核对相应来源与许可。
- `sources[].revision` 可填确实取得的来源修订标识；不知道就省略，不能编造，也不能用 Minecraft 版本号代替。`reviewedAt` 是维护者核对日期，不是来源发布日期或内容快照。首批文档没有固定来源修订号。
- 来源页面修订号只标识文献快照，不自动证明其中每条规则适用 1.20.1。对后续改动、实验开关、服务端数据包或模组影响，在 `versionNote` 与相关章节明确说明。未知的适用性不能写成“已验证”；不能核实的精确数字、概率与配方先不收录。
- 更新文档时检查同篇其他章节与内部链接。不要将查阅日期、现场失败原因或个人试验结果混进普遍机制；有意记录经验时，走经验与技能的独立记录流程。

添加资料后的基本检查是：元数据各值能被 JSON 解析，文档 ID 与章节 ID 不重复，来源可追溯，内部链接存在，搜索能按中英文常用词找到相应章节。版本边界、游戏规则与程序接口的区别应通过内容审查确认。
